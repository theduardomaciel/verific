# i18n — holes to fill later

Current scope is **Brasil only, pt-BR hardcoded**. When internationalization
is picked up, the items below need to be revisited. Each section lists the
file(s) involved and what a proper i18n implementation looks like.

## 1. Phone field (multi-country)

**Current state (BR-only):**

- Frontend: `apps/web/components/ui/input.tsx` → `PhoneInput` stores **E.164**
  (`+55...`) via `toE164BR`/`toNationalBR` in
  `apps/web/lib/validations/masks/phone.ts`; only the visual mask
  (`formatPhone`, `(99) 99999-9999`) is BR-specific.
- Forms builder: `apps/web/components/forms/dynamic/DynamicField.tsx`
  (`case "phone"`) renders `PhoneInput` and stores the **E.164 string**
  (e.g. `"+5582999991234"`, `undefined` when empty).
- Backend: `packages/api/schemas.ts` validates with `isValidPhoneNumber(val)`
  and parses with `parsePhoneNumberFromString(value)` — no default region,
  E.164-only.
- `libphonenumber-js` is a dependency of `packages/api` only. It was removed
  from `apps/web/package.json` when the country selector was dropped.

**To internationalize:**

1. Re-add `libphonenumber-js` to `apps/web`.
2. Restore a country-selector phone input (a previous version existed at
   `apps/web/components/ui/phone-field.tsx` — recover it via
   `git log -- apps/web/components/ui/phone-field.tsx`. Design summary:
   searchable `Combobox` of `getCountries()` with flag emoji + dial code,
   default `BR`, live formatting via `AsYouType`, emitted value normalized to
   **E.164** e.g. `"+5582999991234"`, `""` when empty; followed external values
   whose `+` prefix parsed to a different country).
3. Keep E.164 as the stored canonical form.
4. Validation: select the default region per answer country instead of
   assuming E.164, and validate with `isValidPhoneNumber` + explicit country
   handling.
5. Display: format per viewer's locale instead of the BR mask /
   `formatInternational()` unconditionally (visual-only change, storage untouched).

## 2. Hardcoded pt-BR strings / locale assumptions

- Validation messages in `packages/api/schemas.ts` (`"Telefone inválido."`,
  `"Obrigatório"`, `"E-mail inválido."`, `"Use apenas letras minúsculas, números e _"`, …).
- Form UI placeholders/labels in Portuguese (`"Selecione uma opção"`,
  `"(xx) xxxxx-xxxx"`, `field-dialog.tsx` options, etc.).
- `Intl.DisplayNames(["pt-BR"], …)` was used for country names; locale must
  become dynamic.
- `String.localeCompare(b.name, "pt-BR")` sorting; same treatment.
- `formatAnswerValue` (`packages/api/schemas.ts`): booleans render as
  `"Sim"/"Não"`, dates via `toISOString().slice(0, 10)` (UTC, no locale).
- Date input/display in `DynamicField.tsx` assumes ISO/`yyyy-mm-dd`.

**To internationalize:** introduce a locale provider + message catalog
(e.g. `next-intl`), pass locale into validators/formatters, and replace
hardcoded collation/display strings with locale-aware equivalents.
